# Диагностика падений сервера

Настройки файлового лога и аргументы описаны в [документации сервера](ru-RU/user-docs/server_RU.md#логирование-и-диагностика).

`StackOverflowException` указывает на исчерпание стека вызовов. Типичные причины — неограниченная рекурсия или чрезмерная глубина вложенности. Размер свободной оперативной памяти не определяет доступный стек потока. `System.Object:__icall_wrapper_ves_icall_object_new_specific(IntPtr)` — переход Mono к выделению объекта; единственный этот кадр не определяет вызывающую цепочку и не доказывает превышение размера пакета.

Рабочие гипотезы для расследования:

- повторный вход в загрузку XML и сетевые SyncVar/RPC-хуки;
- циклические связи родительских объектов с рекурсивным обходом;
- рекурсивное логирование из обработчика сообщений или из вызываемого им кода;
- глубоко вложенный XML или другая рекурсивная обработка входных данных. Большая длина пакета сама по себе не означает переполнение стека.

До получения трассы ни одна гипотеза не считается установленной причиной. Патчи диагностики не блокируют сообщения, не изменяют десериализацию и не подавляют исключения игры. На перехват настоящего переполнения стека рассчитывать нельзя: процесс может завершиться до finalizer и последней записи Unity. Для этого `ENTER` пишется и сбрасывается до входа в исследуемую операцию.

Для тестового экземпляра:

```toml
[logging]
logsDir = ''
noLogging = false
logLevel = "Log"
serverDiagnostics = true
```

После падения сохраните файл соответствующего процесса из папки `logsDir` (по умолчанию `BigCityLegacy/logs`). Относительный путь считается от папки игры; также можно указать абсолютный путь. В заголовке есть PID и путь конфига, время — UTC. Последний `ENTER` без парного `EXIT`/`THROW` показывает незавершённую операцию, но сам по себе не доказывает, что причина находится именно в ней. Сопоставляйте записи по ID, parent, depth и thread: несколько потоков могут записываться вперемешку. Растущая глубина с повторяющимися методами — признак повторного входа; при глубине 32 и 64 дополнительно пишется managed stack trace. Размеры буферов и строк помогают сопоставить падение с входными данными. Отсутствие managed стека после аппаратного/нативного сбоя возможно; для такого случая дополнительно нужен нативный crash dump или core dump Mono/Unity.

Остановка после миллиона сообщений устранена отдельно: `NetManagerTools.Update` содержал явный `Application.Quit()`, а консоль BCL — собственный запрос завершения по тому же порогу. Это были счётчики общего числа сообщений, а не доказательство наличия миллиона сохранённых в памяти объектов. На сервере счётчики ограничены, накопление GUI-истории Reporter отключено и записи до установки патчей очищаются. Файлы BCL при этом не очищаются.

Логгер использует потокобезопасную запись без очереди после инициализации, ограниченный ранний буфер (256 записей и 1 МиБ) и защиту от повторного входа. Ошибки диска не пересылаются в Unity; обработчики не читают конфиг повторно, чтобы его собственные сообщения не вызвали рекурсивную загрузку. Каждая запись сбрасывается из managed-буфера в ОС; это защищает от потери очереди при падении процесса, но не является гарантией сохранности при сбое накопителя или потере питания.

Источники: [StackOverflowException](https://learn.microsoft.com/en-us/dotnet/api/system.stackoverflowexception), [Application.logMessageReceivedThreaded](https://docs.unity3d.com/2019.1/Documentation/ScriptReference/Application-logMessageReceivedThreaded.html).
